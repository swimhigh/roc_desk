## 一、背景与目标

roc_desk 现在事实上已经是三种工具的合体：

1. 类似 WindTerm/MobaXterm 的 **SSH/Agent/RDP 远程会话工具**（`HomeShell.tsx` 左侧会话树 + 右侧标签）；
2. 类似 VS Code 的 **工作区 IDE**（`App.tsx` 主体：Explorer + 编辑器 + 终端 + SFTP + AI 工具）；
3. 一个还很单薄的 **独立编辑器壳**（`App.tsx` 里 `standaloneShellVisible` 那一块：没有工作区，只有 tab 栏 + Monaco，靠拖拽/`Ctrl+O`/文件关联触发）。

未来还会加第 4 种：

4. 类似 Total Commander 的 **本地双栏文件管理器**（尚未实现，可复用 `SftpBrowser`/`AgentBrowser` 的双栏骨架改造成本地-本地）。

用户的诉求是把这四种能力提升为平等的「**工作模块**」，并且明确要求一种"类似桌面"的架构：**固定一个常驻的首页（启动器，默认最大化窗口），点开某个工作模块时另起一个新的进程和窗口**，同一个模块也可以开多个窗口/多个进程并行工作。

这个架构确定后，用户明确指出：**不再需要"分目录运行 exe 来固定/记住工作模式"这套机制了**——那本来是"单进程、想要多个模式并行"这个限制下的变通方案（跑多份 exe、每份各卡死在一个模式），现在首页本身就能按需 spawn 任意数量、任意模块的窗口，直接在首页点一下就是新窗口，不需要再靠"物理分目录"这种迂回方式表达"我要几个不同模式同时开着"。因此本设计里**只有一份数据目录、一份数据库**，不需要 `--data-dir`、不需要按目录记忆模式，见 §3.6。

这与现状有两处根本性冲突，必须先讲清楚：

- 现在的首页（`HomeShell.tsx`）不是"模块启动器"，而是"会话树和工作区选择器常驻同屏、且和模块内容挤在同一个窗口/同一个进程里"——这是 2026-08-25 的一次明确产品决策（见 DESIGN.md §3.9 引用的用户原话），本次改造是**推翻重做**，不是加一个新 tab。
- "首页常驻 + 点模块另开一个独立进程窗口，且同一模块能开多个窗口"这件事，现在的 `tauri-plugin-single-instance` 配置会直接拦下来（细节见下一节）——这是本设计能否成立的地基，必须先解决。

## 二、现状盘点

### 2.1 三块界面现在各自的位置

| 现有实现 | 对应的目标模块 | 触发方式 | 状态保活 |
|---|---|---|---|
| `components/RemoteTool/HomeShell.tsx` | SSH 桌面模块 | 应用没打开工作区时的默认首页 | `remoteSessionStore` 拍平数组 + display 切换，已保活 |
| `App.tsx` 主体（`current` 非空分支） | 工作区（VS Code）模块 | 从 `HomeShell.tsx` 右侧 `WorkspacePicker` 打开工作区 | `terminalStore` 有界 LRU 保活 + `editorStore` 工作区标签，已保活 |
| `App.tsx` 里 `standaloneShellVisible` 分支 | 编辑器（UltraEdit）模块 | 拖拽文件/`Ctrl+O`/系统"打开方式"，只在**没打开过工作区**时才有意义 | `editorStore` 游离标签，已保活，但只是工作区模块的"降级兜底"，不是一等入口 |
| （不存在） | 资源管理器（Total Commander）模块 | — | — |

这三块现在全部挤在**同一个进程、同一个顶层窗口**里，靠"多棵子树常驻挂载、只切 `display`"切换可见性。本设计要把它们拆成**各自独立的进程和窗口**，下面 §三 详细展开。

### 2.2 关键技术约束：`single-instance`

这一节是调研后发现的硬约束，直接决定"首页常驻 + 模块另开进程窗口"这个架构能不能做、怎么做。

`tauri-plugin-single-instance`（`Cargo.toml` 引入的 `2.4.4` 版本）在 Windows 上的实现（`platform_impl/windows.rs`）用来判断"是否已有实例在跑"的命名互斥体/窗口类名，**完全由 `tauri.conf.json` 里的 `identifier`（`com.rocdesk.desktop`）拼出来，是系统全局唯一的一个值，和进程是从哪里、带什么参数启动的毫无关系**：

```rust
let id = app.config().identifier.clone();               // 固定值："com.rocdesk.desktop"
let mutex_name = encode_wide(format!("{id}-sim"));       // 系统全局命名互斥体
// CreateMutexW 拿到 ERROR_ALREADY_EXISTS 就 FindWindowW 找到已有实例的隐藏窗口，
// WM_COPYDATA 把 cwd + argv 转发过去，然后 std::process::exit(0) 自杀。
```

也就是说：**今天首页进程 spawn 一个 `roc_desk.exe` 子进程去开"工作区模块"窗口，这个子进程刚起来就会撞上和首页同一个全局互斥体，被首页"吞掉"**（转发参数、聚焦首页窗口、自己退出）——完全没法达到"点一个模块另开一个真进程真窗口"的效果。这是本设计必须优先解决的地基问题，方案见 §3.7。

顺带一提，`resolve_app_data_dir()`（`src-tauri/src/lib.rs:56`）已经是"便携式"的——数据目录是 `当前 exe 所在目录/.rock_desk`。本设计不需要动它：启动器和它 spawn 出来的所有模块窗口都是同一个 exe 文件重新执行出来的进程，天然解析到同一个数据目录，不用显式传递或另外设计（§3.6）。

DESIGN.md §十 开放风险第 7 条提到的"多工作区并行状态"（`AppState` 是进程级单例，同进程开多窗口会有 SSH 连接池共享问题）在本设计里**天然不适用**：每个模块窗口都是独立进程、独立 `AppState`，不存在"同进程内多窗口共享连接池"这回事——用真进程隔离换来的直接好处。

## 三、总体设计

### 3.1 术语

- **启动器（Launcher）**：首页所在的进程，职责单一——展示模块面板、承接"打开模块/最近项"的点击、把请求转成子进程 spawn。不承载任何模块自己的内容（不内嵌 SSH 会话树、不内嵌编辑器）。
- **模块窗口（Module Window）**：由启动器（或直接由快捷方式）拉起的另一个 `roc_desk.exe` 进程，进程启动参数固定了它只渲染四种工作模块中的哪一种，全屏承载该模块的完整功能，不含首页仪表盘、也不含其它模块的隐藏内容。
- **工作模块（Module）**：`ssh` / `workspace` / `editor` / `explorer`（第四种暂未实现，先占位）四选一。

### 3.2 四种工作模块

| 模块 | 定位 | 复用的现有实现 |
|---|---|---|
| **SSH 桌面**（`ssh`） | WindTerm/MobaXterm 式：会话树 + SSH/Agent 终端 + SFTP + RDP | `HomeShell.tsx` 减去右侧 `WorkspacePicker` 之后剩下的部分：`SessionTree` + `remoteSessionStore` 标签体系 |
| **工作区**（`workspace`） | VS Code 式：Explorer + 编辑器 + 终端 + SFTP + AI 工具 | `App.tsx` 现有主体（`current` 非空分支）原样保留 |
| **编辑器**（`editor`） | UltraEdit 式：不依赖工作区、专注多标签文本/二进制编辑 | `App.tsx` 现有 `standaloneShellVisible` 分支，提升为独立进程的一等模块（见 §3.5） |
| **资源管理器**（`explorer`，未来） | Total Commander 式：本地双栏文件管理 | 暂无实现；首页先给"敬请期待"占位卡片，不阻塞本次改造 |

### 3.3 架构选择：单进程切模块 vs 启动器 + 模块子进程

有两条候选路线，先摆出来对比，再定结论：

| | A：单进程内切模块（上一版草案） | B：启动器 + 模块子进程（本版采用） |
|---|---|---|
| 窗口/进程数 | 全程 1 个进程 1 个窗口，模块靠 `display` 切换可见性 | 启动器 1 个进程 + 每个打开的模块各 1 个独立进程/窗口 |
| 同模块开多个（如两个工作区窗口） | 做不到——同一进程内一份 `editorStore`/`terminalStore` 撑不住"两个独立工作区各自的状态"同时存在 | 天然支持——每个进程各自完整状态，互不相关 |
| 崩溃隔离 | 无——任何一个模块内部 panic 影响整个进程/窗口 | 有——一个模块窗口崩溃不影响启动器和其它模块窗口 |
| 内存/启动开销 | 低——只有一份 WebView2 运行时 | 较高——每开一个模块窗口就是一份独立的 WebView2 运行时（现代 WebView2 有共享运行时机制，增量开销小于"从零起一个浏览器"，但仍明显高于同进程多窗口） |
| 实现复杂度 | 中——四棵子树常驻 + 一个模式状态机 | 中偏高——需要重做 `single-instance`、进程间"回首页"信令、启动参数路由 |
| 是否匹配"类似桌面，点图标开新窗口"的直觉 | 弱——本质还是一个软件内部切标签 | 强——和 Windows 本身"任务栏开多个独立窗口"的心智模型一致 |

**结论：采用 B**。用户明确要"新的进程和窗口"，且"同一模块可以开多个窗口"这一条在方案 A 下无法满足，只有 B 能做到。内存/启动开销是明确接受的代价，不是需要回避的顾虑（见 §七 风险 1）。

### 3.4 启动器（首页）设计

```
┌────────────────────────────────────────────────────────────────────────┐
│                              roc_desk                          最大化 □ ✕│
│                                                                          │
│  ┌───────────────────┐  ┌───────────────────┐                          │
│  │ 🖥  SSH 桌面        │  │ 📁  工作区          │                          │
│  │  web-01 · root@..  │  │  my-app  F:\code\..│                          │
│  │  db-slave · root@..│  │  nginx-conf  root@.│                          │
│  │  [+ 新建连接]        │  │  [+ 打开文件夹/连接] │                          │
│  └───────────────────┘  └───────────────────┘                          │
│  ┌───────────────────┐  ┌───────────────────┐                          │
│  │ 📝  编辑器          │  │ 🗂  资源管理器 (预告) │                          │
│  │  notes.md          │  │  即将推出            │                          │
│  │  deploy.sh          │  │                     │                          │
│  │  [+ 打开文件]        │  │                     │                          │
│  └───────────────────┘  └───────────────────┘                          │
└────────────────────────────────────────────────────────────────────────┘
```

- **默认最大化**：启动器窗口创建后立即 `maximize()`（Tauri `WebviewWindowBuilder` 支持 `.maximized(true)`，或 setup 阶段拿到窗口句柄后调用一次），符合"类似桌面首页"的定位——不是一个可以随便缩小的工具面板。
- 每个分区展示"图标 + 模块名 + 该模块下的最近/常用列表"。点区域标题/图标 → spawn 一个该模块的"空白"子进程（SSH 桌面看到会话树但没打开标签、工作区模块看到 `WorkspacePicker`、编辑器模块看到空标签栏）；点区域里的具体项（某个连接/某个工作区/某个最近文件）→ spawn 子进程时带上"直接打开这一项"的参数，跳过中间步骤。
- 首页本身**不重新实现**"新建连接""打开文件夹"这些管理功能——`[+ 新建连接]`/`[+ 打开文件夹/连接]` 这类按钮只是快捷方式，点了 spawn 对应模块的子进程并唤起原有弹窗（`ConnectionDialog`/`RemoteWorkspaceDialog` 等），完整的增删改查还是在模块窗口内部用现成 UI 做，避免两套入口维护两份逻辑。
- 资源管理器区在未实现前直接置灰/显示"即将推出"，不做成可点。
- spawn 子进程是"发射后不管"——调用 `std::process::Command::new(current_exe)` 加参数后 `.spawn()`，不等待子进程退出，也不阻塞首页 UI；首页可选地（非必须）监听子进程是否还存活，给对应分区打一个"运行中"的绿点，用于用户已经开了某个模块窗口、又跑回首页想确认"我是不是已经开过了"的场景。
- 首页是**强单例**（只应该有一个首页），重复启动（无参数双击 exe）应聚焦到已存在的首页窗口，不新开——见 §3.7。

### 3.5 模块窗口（子进程）设计

每个模块子进程本质上是"单模块版"的 roc_desk：启动参数（见下）固定了它只渲染四种模块中的一种，是一个完整独立的顶层窗口，不含首页仪表盘、也不含其它模块的隐藏子树——这比上一版"单进程内五棵子树常驻"更简单：每个进程只需要关心自己这一种模块的状态，不用操心"切走了要不要保活"（因为这个进程本来就只做这一件事，直到窗口关闭、进程退出）。

启动参数（草案）：

```
roc_desk.exe --mode=workspace --open=<workspace_id> --spawn-token=<uuid>
```

- `--mode`：`ssh` | `workspace` | `editor` | `explorer`，决定这个进程渲染哪个模块，必填（不传则是启动器模式）。
- `--open`：可选，直接定位到某个具体项（工作区 id / 连接 id / 文件路径），对应首页点"具体项"而不是点"模块标题"的场景。
- `--spawn-token`：一次性 uuid，标记"这是首页派生出来的窗口"，用于 §3.7 的 single-instance key 生成（决定这个窗口是否允许和同模块的其它窗口共存）。

不需要 `--data-dir`：子进程和首页是同一个 exe 文件重新执行出来的，`resolve_app_data_dir()` 天然解析到同一个目录，数据（连接列表/工作区列表/设置）本来就是共享的，不需要显式传递或做任何隔离设计（§3.6）。

模块窗口内部布局**原样复用现有代码**：`ssh` 对应现有 `HomeShell.tsx` 去掉工作区选择器后的部分，`workspace` 对应现有 `App.tsx` 主体，`editor` 对应现有 `standaloneShellVisible` 分支，逻辑不用重写，只是从"同一个 App 组件内部按状态切换渲染分支"改成"启动参数决定这个进程从一开始就只挂载这一棵子树"。

**模块窗口内部原有的"切换"能力原样保留，不受多进程改造影响**——`--mode`/`--open` 只决定这个进程**刚启动时**渲染成什么、打开哪一项，不代表这个窗口从此焊死在这一项上：

- `workspace` 模块窗口保留现有 `App.tsx` 顶部"工作区名 ▾"下拉（`switchWorkspace`，见 `App.tsx:454`）——点开下拉选另一个最近工作区，还是像现在一样**在同一个窗口/同一个进程内**原地切换 `current`，重置该窗口的 Explorer/编辑器/终端状态，不会另起新窗口、也不涉及 spawn 或 single-instance。这是"进程内切换"，和"开一个新窗口"是两件不同的事。
- 同理 `ssh` 模块窗口保留 `SessionTree` 里点开另一个连接、`editor` 模块窗口保留标签栏点开另一个文件——都是模块窗口原有的"进程内切换/多开标签"能力，本设计不改动这部分。
- 只有当用户明确要"另开一个独立窗口/独立进程"时（首页点击，或未来给 `switchWorkspace` 下拉加一个"在新窗口打开"选项，类似 VS Code），才会走 §3.4 的 `spawn_module_window`；这属于可选的后续增强，不是本次改造的必需项，因为首页本身已经能满足"开新窗口"的诉求。

**同一模块可以开多个窗口**：比如从首页"工作区"分区分别点两个不同的最近项，各自 spawn 一个独立子进程，两个窗口互不相关，各自的终端/编辑器状态互相独立——这是方案 B 相对方案 A 的核心收益，不需要额外设计，是多进程架构的自然结果。

**模块窗口里的"返回首页"**：模块窗口标题栏/工具栏保留现有的 Home 图标按钮，但语义从"在本进程内切回首页子树"改成"唤起启动器进程"：

1. 用启动器固定的 key（§3.7）去 `FindWindowW` 探测启动器窗口是否还活着；
2. 找到 → 发一条现有 single-instance 机制同款的 `WM_COPYDATA`/等价 IPC 消息，请求它 `unminimize()` + `set_focus()`；
3. 没找到（用户之前把首页关了）→ `Command::new(current_exe)` 不带 `--mode` 重新 spawn 一个新的启动器。

点"返回首页"**不会关闭当前模块窗口**——它只是把用户的注意力带回首页，模块窗口该开着继续开着，这也符合"多个模块窗口并行工作，首页只是发射台"的定位。

**关闭语义**：

- 关闭一个模块窗口 → 该进程退出，不影响首页或其它模块窗口。
- 关闭首页窗口 → 首页进程退出，不影响任何已经打开的模块进程（操作系统层面它们本来就互相独立）。
- 首页和所有模块窗口都关闭后，应用才算完全退出；不需要额外做"守护进程"或"托盘常驻"，符合 Windows 桌面程序的一般预期。

### 3.6 数据与状态：全部共享，不需要分目录

首页是唯一入口，所有模块窗口都由它 spawn 出来，**天然共用同一个 `app_data_dir`、同一份数据库**（连接列表/工作区列表/设置）——不设计任何"每个进程/每个窗口各自一份数据"的机制，也不需要 `--data-dir` 这类参数：

- 用户最初设想的"分目录运行 exe、记住并固定某个工作模式"，本质诉求是"能同时开着多个不同模式的窗口"；这个诉求现在由首页 + `spawn_module_window` 直接满足——在首页点几下就能开出任意组合的模块窗口，不需要靠"物理上放在不同目录、每份 exe 卡死一个模式"这种迂回方式表达。
- 因此**不引入 `--data-dir` 参数、不做按目录的隔离设计**，`resolve_app_data_dir()` 保持现状不动。
- "记住上次打开的具体项"这件事不需要专门的持久化机制——首页每个分区的"最近/常用列表"（§3.4）本来就来自现有的 `workspaceService`/`connectionService` 的"最近"查询，点开就是恢复到上次那个具体工作区/连接，不需要额外的 `instance_state` 文件。

如果确实存在"一台机器上跑两套完全互相看不见的连接列表/工作区列表"（比如公司和私人账号分开）这种小众场景，直接装两份完全独立的便携版目录即可——这是"便携版"这个部署形态本来就有的能力，和本设计无关，不需要额外的命令行参数支持。

### 3.7 `single-instance` 改造

同一套 Win32 原生逻辑（`CreateMutexW` 探测 → 存在则 `FindWindowW` + `WM_COPYDATA` 转发后退出 → 不存在则注册消息窗口接收后续转发，源码见 `tauri-plugin-single-instance` 的 `platform_impl/windows.rs`）继续复用，但**互斥 key 的生成方式按进程角色分两种**（该插件本身在 Windows 平台没有开放自定义 key 的 hook，所以这部分要放弃插件、自己写一份等价实现）：

| 进程角色 | key 生成方式 | 效果 |
|---|---|---|
| 启动器（无 `--mode`） | `identifier + "-launcher"` | 稳定 key——和现有插件默认行为等价：启动器双开，第二次被拦下、转发给第一个、聚焦它 |
| 快捷方式直接启动的模块窗口（有 `--mode`，无 `--spawn-token`，可选便利，见下） | `identifier + "-fixed-" + mode` | 稳定 key——同一个"固定快捷方式"手滑连点两次只会聚焦已经开着的那个窗口，不会开出一堆重复窗口 |
| 首页派生的模块窗口（有 `--mode` 且有 `--spawn-token`） | `identifier + "-spawned-" + spawn_token`（每次 spawn 生成的一次性 uuid） | 一次性 key——恒定不会和任何其它进程的 key 相同，等价于"关闭这个窗口的 single-instance 检查"，允许同一模块同时开多个窗口 |

三种 key 共用同一段 `CreateMutexW`/`FindWindowW`/`WM_COPYDATA` 代码，区别只是传进去的字符串怎么拼——实现上是一个函数、三个调用点，不是三套逻辑。"固定快捷方式"（第二行）是一个顺手就能提供的可选便利（比如有用户就是想给"工作区模块"单独钉一个任务栏图标），不是本次要重点交付的东西，核心诉求（首页 + 按需开多个模块窗口）不依赖它。

> **实现落地时的调整**：最终没有照这张表自己写 `CreateMutexW`/`FindWindowW`/`WM_COPYDATA`。
> 落地方案更简单——`tauri_plugin_single_instance::init(...)` 这一行插件调用**只在没有
> `--mode`（即启动器角色）时才注册**，带 `--mode` 的模块窗口完全不注册这个插件，等价于
> 上面"一次性 key"想达到的效果（模块窗口永远不会被任何互斥体拦下），却不用碰任何 Win32
> 原生 API，也不需要 `--spawn-token` 这个参数。代价是放弃了"固定快捷方式"那一行的去重
> 能力（同一个固定 `--mode` 快捷方式连点两次会真的开两个窗口）——上面原文已经说了这只是
> "可选便利，不是重点"，实际做的时候判断这点代价换掉一整段自实现 Win32 逻辑很划算。
> 首页角色的 key 仍然是插件默认行为（等价原表第一行），未改动。详见 `src-tauri/src/lib.rs`
> 的 `run()` 函数开头。

## 四、数据与代码改动清单（供实现阶段参考，非最终 API）

**后端（`src-tauri/src`）**

- `lib.rs`：解析启动参数（`--mode`/`--open`/`--spawn-token`），决定这次启动是"启动器"还是"某个模块窗口"，并据此选择 §3.7 的 key 生成策略、决定要挂载哪些 Tauri command/state（模块窗口大概率不需要启动器专属的"扫描最近项列表"逻辑，启动器也不需要模块窗口专属的一些运行时状态，可以按角色裁剪，减少不必要的初始化开销）。数据目录解析（`resolve_app_data_dir()`）不需要改动。
- 新增小模块（如 `single_instance_custom.rs`）替换现有 `tauri_plugin_single_instance::init(...)` 这一行插件调用，按 §3.7 的三种 key 规则生成互斥体/窗口名。这一步涉及 Windows 原生 API，建议单独一次真机验证，不要和其它改动混在一起测。
- 新增一条 Tauri command（如 `spawn_module_window(mode, open)`），内部 `std::process::Command::new(std::env::current_exe()?)` 拼参数后 `.spawn()`，供首页前端调用；同时生成 `--spawn-token` 的 uuid。
- 新增"聚焦启动器"的探测逻辑（模块窗口点"返回首页"时用）：按启动器的稳定 key 做一次 `FindWindowW`，找到就转发一条聚焦请求，找不到就走上面的 `spawn_module_window` 逻辑（不传 `--mode`，即拉起一个新启动器）。

**前端（`src-web/src`）**

- 新增 `components/Home/HomeDashboard.tsx`：全新的首页组件，只做"展示分区 + 调 `spawn_module_window`"，不内嵌任何模块内容；替换现有 `App.tsx` 里 `!current` 时渲染 `HomeShell.tsx` 的入口。启动器进程的 `App.tsx`（或新建一个 `LauncherApp.tsx`）只挂载这一个组件。
- 模块窗口进程的入口需要能"只挂载一种模块"：`main.tsx`/`App.tsx` 读取 Tauri 启动时传入的 `--mode`（通过现有 `take_pending_open_paths` 同款的一次性 command，或直接读 `env::args()` 转发到前端），据此只渲染对应模块的组件树，不再需要"5 棵子树 + `display` 切换"那一套（每个进程本来就只有 1 棵子树）。
- `HomeShell.tsx` 拆分：会话树+标签逻辑收进 `ssh` 模块自己的容器组件（原地保留、职责收窄即可，不用整体重写）；右侧 `WorkspacePicker` 的"最近工作区"清单复用到 `workspace` 模块窗口的空白态，同时首页仪表盘的"工作区"分区也要一份精简版（复用同一个数据源/`workspaceService`，不用重新查）。
- 各模块窗口标题栏新增"返回首页"按钮的新语义（§3.5），替换现有 `App.tsx`/`HomeShell.tsx` 里"Home 图标 = 切回本进程内首页子树"的旧实现。
- 编辑器模块补一个"最近打开文件"列表的持久化并接入首页仪表盘（目前游离文件标签只在 `editorStore` 内存里，没有独立于工作区标签之外的"最近文件"记忆）。

## 七、风险与开放问题

1. **每个模块窗口一份 WebView2 运行时的资源开销**：这是方案 B 相对方案 A 明确接受的代价（§3.3），但需要实测量化——同时开 3-4 个模块窗口（比如 SSH 桌面 + 两个工作区 + 一个编辑器）时的内存占用和启动耗时是否在可接受范围，建议 Phase 2 落地后专门测一轮，超出预期再考虑"同类模块共享部分运行时"之类的优化（复杂度高，不预先设计，按需再做）。
2. ~~**Windows 原生 API 改造的不确定性**~~：**未发生**——§3.7 落地时改用"模块窗口不注册插件"这个更简单的方案，完全没碰 `CreateMutexW`/`FindWindowW`/`WM_COPYDATA` 这类 native 调用，这条风险随之消失。
3. ~~**跨进程"返回首页"信令的可靠性**~~：**未发生，原因同上**——"返回首页"按钮直接 spawn 一个不带 `--mode` 的新进程，是否需要转发/聚焦完全交给插件默认逻辑处理，不存在"区分转发文件路径请求 vs 纯聚焦请求"这个问题。
4. **任务栏窗口数量膨胀**：一个用户如果开习惯了五六个模块窗口，任务栏会明显变挤，比单进程多标签更占"窗口位"。可以后续考虑给模块窗口设置统一的任务栏分组图标/`AppUserModelID` 让 Windows 把它们分组显示，但这是体验优化，不阻塞本次架构改造。
5. **首页分区 vs 模块内部选择器的职责边界**：首页每个分区的"最近/常用列表"和模块窗口内部原有的 `SessionTree`/`WorkspacePicker` 存在信息重叠，需要在实现时明确首页只做"跳转捷径"，不重新实现管理类交互（新建/编辑/删除），否则会出现两套入口两份状态维护成本。
6. **编辑器模块的功能对标度**：定位对标 UltraEdit，但目前只是多标签 Monaco，尚不具备十六进制查看、编码批量转换、大文件流式编辑、多文件批量替换等 UltraEdit 特色能力——这些是编辑器模块的后续功能规划，不在本次"首页/模块架构"改造范围内，此处只作提示。
7. **资源管理器模块的技术方案未选型**：本地-本地双栏具体怎么复用现有 `SftpBrowser`/`AgentBrowser` 组件（拆公共骨架 vs 新写）尚未设计，Phase 4 启动前需要单独过一轮设计，本文档只占位。
