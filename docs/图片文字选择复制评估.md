# 编辑器图片文字选择与复制评估

## 结论

当前图片预览使用原生 `<img>`，图片像素中没有文本 DOM，因此不能直接选择图片中的文字。要支持鼠标选中、`Ctrl+C` 复制，必须增加 OCR，并在图片上方绘制一个与图片坐标同步的可选文字层。

建议第一版采用 **Windows 原生 OCR**：OCR 代码放在 Tauri Rust 后端，前端只负责展示文字框和处理选择复制。这样不需要把中文识别模型塞进 `roc_desk.exe`，安装包增量很小；识别语言由 Windows 已安装的 OCR 语言包提供。`Windows.Media.Ocr` 和 `SoftwareBitmap` 在 Windows 10、Windows 11 均可用，客户端不需要区分两套实现。

## 需要改造的部分

### 1. 图片查看器

在 `src-web/src/components/Editor/ImageViewer.tsx` 增加“识别文字”按钮、识别中状态、识别失败提示和“复制全部文字”操作。现有缩放、双击放大、拖拽平移逻辑需要抽成统一的图片变换参数，图片和文字层必须使用同一套 `scale/offset`，否则放大或拖动后文字框会漂移。

文字层可采用绝对定位的透明/半透明 `span`：

- OCR 返回每行或每个单词的文字和像素矩形；
- 按原图尺寸计算百分比坐标；
- 文字层允许 `user-select: text`，图片层继续禁止拖拽；
- 点击或拖选后由浏览器处理复制，保留“复制全部识别文字”按钮作为兜底；
- 图片旋转、EXIF 方向、缩放、平移、窗口 resize 都必须同步更新文字层。

### 2. Tauri OCR 命令

新增一个只读命令，例如 `editor_ocr_image`，输入工作区/文件来源、图片 MIME 和 base64（或后续改成后端按路径读取），返回图片尺寸、语言、识别行和单词矩形。Windows 实现使用 `Windows.Media.Ocr.OcrEngine` 和 `Windows.Graphics.Imaging` 解码图片。需要在 `src-tauri/Cargo.toml` 的 `windows` features 中加入对应的 Imaging/Media/OCR/Runtime API，并在非 Windows 平台返回“当前平台暂不支持原生 OCR”。

### 3. 语言、缓存和远程文件

默认优先使用系统中文 OCR，找不到时回退到系统默认语言，并提示安装 Windows 10/11 的中文“文字识别/OCR”语言包。OCR 不应上传云端。缓存键建议为“图片路径 + 文件 mtime/size + OCR 语言 + 图片内容 hash”，第一版可使用前端内存缓存，稳定版再写入 SQLite。当前远程图片也已经读成 base64，第一版可复用这条链路。

## EXE 体积估算

当前便携版 `bin/roc_desk.exe` 约 **46.1 MB**。实际增量如下：

| 方案 | EXE/安装包预计增量 | 说明 |
| --- | ---: | --- |
| Windows 原生 OCR（推荐） | 约 **0.3–1.5 MB** | 只增加 Rust 调用代码；中文识别模型由 Windows 语言包提供 |
| Tesseract.js | 约 **8–60+ MB** | WASM 和 `eng`/`chi_sim` 等模型文件是主要体积 |
| Tesseract 原生 EXE | 约 **20–60 MB** | 还要增加外部进程和部署维护成本 |
| 云端 OCR | 接近 **0 MB** | 需要上传图片、网络和服务费用 |

原生 OCR 语言包占用的是 Windows 系统空间，不会打进 `roc_desk.exe`。

## 实施步骤

1. 在 Windows 验证 OCR 语言包检测和不可用时的提示。
2. 增加 Rust OCR 命令和返回结构，覆盖空图、旋转图、超大图限制。
3. 在 `ImageViewer` 增加识别按钮、加载态、失败态和“复制全部”。
4. 实现可选文字 overlay，验证缩放、平移和窗口 resize 后坐标对齐。
5. 加入内存缓存、图片修改失效和 OCR 超时，避免阻塞 WebView 子进程。
6. 验证本地、SSH、Agent 三种来源，再执行前端、Rust 和便携版构建。

## 风险和边界

OCR 对低清晰度、倾斜、手写体和复杂表格可能误识别；“复制全部文字”较容易实现，“像网页一样精确拖选任意区域”需要逐词 bounding box，开发量更高。若必须跨平台并保证离线语言一致，应选 Tesseract.js，但体积和内存成本会明显增加。
